## 二、GitHub Secrets（仓库 Settings → Secrets and variables → Actions）

| Secret                  | 内容                   | 最小权限建议                                    | 缺失时的行为                               |
| ----------------------- | ---------------------- | ----------------------------------------------- | ------------------------------------------ |
| `CLOUDFLARE_API_TOKEN`  | Cloudflare API Token   | **Pages Edit + D1 Edit**（勿给账户级 All Edit） | 部署步骤跳过（不红叉），冒烟测试跳过       |
| `CLOUDFLARE_ACCOUNT_ID` | Cloudflare 账户 ID     | —（标识用，非凭证）                             | 同上                                       |
| `D1_DATABASE_ID`        | `1df7e200-…`（见上表） | —（标识用，非凭证）                             | save-history 跳过 D1 同步，D1 核查步骤跳过 |

凭证安全约定：

- Token 只从 Secrets 读取，**任何脚本/代码/日志不得硬编码或回显**（`scripts/lib/d1.mjs` 已按此实现）。
- Token 权限遵循最小化：Pages Edit + D1 Edit 即可覆盖全部现有流程（部署 + 读写 D1）。
- 怀疑泄露时：Cloudflare 控制台 → My Profile → API Tokens 直接**吊销重建**，再到仓库 Secrets 更新，无需改任何代码。
- 轮换建议：随人员变动或至少每年一次。

## 三、两个工作流的分工

| 工作流              | 触发方式              | 做什么                                                                               |
| ------------------- | --------------------- | ------------------------------------------------------------------------------------ |
| `deploy.yml`        | push 到 `main` / 手动 | 质量门禁 → 构建 → `pages deploy dist --project-name=jiuxi` → **冒烟测试** → ZAP 扫描 |
| `refresh-feeds.yml` | 每小时 cron / 手动    | 构建 → fetch-feeds 抓取注入 → **D1 核查** → 同样 `pages deploy`                      |

两个工作流的部署 job 共用 `jiuxi-deploy` 并发组，不会交错上传。

### 冒烟测试（deploy.yml，v1.7.1 新增）

部署完成后自动请求三个端点，把「Pages Functions 静默失效」转为 CI 红灯：

- `GET /api/history?days=7`
- `GET /api/feed?aggregate=1&section=ai&s=…`（服务端聚簇）
- `GET /api/candidates?section=ai`

判定规则：

- **红灯**（退出码 1，工作流失败）：任一端点连续 3 次不返回 `application/json`——即 Pages Functions 未部署/未编译（历史 P0 故障态：所有路径返回 index.html）。
- **黄灯**（warning，不阻断）：返回 JSON 但带 `d1_binding_missing` / `query_failed`——链路通，D1 配置或数据层有问题，按提示到控制台排查。
- **绿灯**：全部规范 JSON。

### D1 写穿核查（refresh-feeds.yml，v1.7.1 新增）

fetch-feeds 写入后经 Cloudflare REST API 查 `snapshots` 表：0 行 / 超过 2 小时未更新 / 查询失败 → warning。save-history 的设计是「失败不阻断构建」（云端故障不拖垮定时重建），本步骤补上可见性。

## 四、控制台操作路径（常见任务）

| 任务                  | 路径                                                                                      |
| --------------------- | ----------------------------------------------------------------------------------------- |
| 看部署记录            | Pages 项目 `jiuxi` → Deployments                                                          |
| 查 Functions 部署状态 | Pages 项目 `jiuxi` → Settings → Functions → Deployment history                            |
| 配/查 D1 绑定         | Pages 项目 `jiuxi` → Settings → Functions → D1 database bindings（binding 名必须为 `DB`） |
| 查 D1 数据            | D1 数据库 `jiuxi-history` → Console（`SELECT * FROM snapshots LIMIT 5`）                  |
| 吊销/重建 API Token   | My Profile → API Tokens                                                                   |
| 看 Actions 运行       | GitHub 仓库 → Actions                                                                     |

> ⚠️ **D1 绑定只认 `wrangler.toml`**：`wrangler.toml` 含 `pages_build_output_dir` 时是 Pages 配置的唯一事实来源，每次 `wrangler pages deploy` 用它覆盖云端设置——只在仪表盘里绑的 D1 会被一次部署抹掉（2026-10 实测复现）。当前绑定已声明在 `wrangler.toml` 的 `[[d1_databases]]`，随部署自动同步。

## 五、本地接管 checklist

接手人按序核对，全部打勾即完成接管：

1. [ ] 被拉入 Cloudflare 账户（或拿到自建账户 + 上述资源迁移方案）
2. [ ] 拿到 GitHub 仓库写权限（push `main` 即触发部署）
3. [ ] 三个 Secrets 已在仓库配置（见表二；缺失时部署自动跳过，不会报错——要主动确认）
4. [ ] `wrangler.toml` 的 D1 绑定未被人从控制台侧改动（见表四警告）
5. [ ] 手动跑一次 `deploy.yml`（Actions → Deploy 九溪 → Run workflow），确认冒烟测试绿灯
6. [ ] 手动跑一次 `refresh-feeds.yml`，确认 D1 核查 notice 正常
7. [ ] 访问 `https://jiuxi-bm1.pages.dev/` 与 `/history/`（历史回顾页）验证内容与接口

## 六、应急操作

| 症状                        | 第一动作                                                                          |
| --------------------------- | --------------------------------------------------------------------------------- |
| 冒烟测试红灯（API 返 HTML） | 看 deploy job 的 wrangler 日志 → 控制台 Functions 部署状态 → 核对 `wrangler.toml` |
| D1 核查 warning「0 行」     | 核对 Secrets 权限（D1 Edit）→ 看 job 日志里 save-history 的 ☁️/⚠️ 行              |
| 线上内容陈旧                | 看 `refresh-feeds.yml` 最近一次运行是否成功（GitHub 高频 cron 可能延迟）          |
| 需要立刻回滚                | Pages 项目 → Deployments → 选历史部署 → Rollback（静态部分秒级回退）              |
